# مسیر فایل در نسخهٔ ۰٫۵

## رفت و برگشت واقعی

پنل/ایجنت → پرامپت JSON و ثبت Job → موتور حساب → دریافت URL یا base64 → فایل موقت → اعتبارسنجی → انتشار فایل اصل → ثبت SQL → گالری → دانلود اصل/ZIP.

در این نسخه ورودی تولید، پرامپت متنی است. Upload تصویر مرجع به موتور و image editing هنوز پیاده نشده‌اند؛ ادعای انتقال فایل ورودیِ پشتیبانی‌نشده نداریم.

## دریافت و ذخیره

- درخواست به موتور `response_format=url` دارد. اگر موتور پاسخ base64 بدهد، همان پاسخ در بودجهٔ JSON پذیرفته می‌شود؛ درخواست تولید دوباره برای fallback ارسال نمی‌کنیم.
- کل JSON موتور حداکثر ۳۲ MiB است. دریافت آن روی فایل موقت دیسکی انجام می‌شود و سپس JSON parse می‌شود. خود parse و رشتهٔ base64 همچنان حافظه مصرف می‌کنند؛ کل مصرف سیستم ۲۵۶ KiB نیست.
- URL فقط HTTP روی loopback و پورت همان حساب و مسیر تصویری مشخص است. Redirect، آدرس بیرونی، userinfo، query و fragment پذیرفته نیستند. برای این ترافیک محلی، پراکسی محیط غیرفعال است.
- دریافت URL با قطعات حداکثر ۲۵۶ KiB و کنترل اندازهٔ واقعی پیش می‌رود؛ به Content-Length تنها اعتماد نداریم. base64 نیز قبل از decode از نظر اندازه بررسی و در مرزهای معتبر، قطعه‌ای decode می‌شود.
- فایل تصویر حداکثر ۶۴ MiB و ۹۰ میلیون پیکسل است؛ فقط PNG/JPEG/WebP پذیرفته می‌شود. اعتبارسنجی فایل و SHA-256 ثبت می‌شوند.
- فایل در همان filesystem با نام موقت نوشته، flush و fsync می‌شود. پس از اعتبارسنجی، hard link با نام نهایی ساخته می‌شود؛ این انتشار اتمیک است و فایل موجود را بازنویسی نمی‌کند. مسیر داده باید filesystem دارای hard-link داشته باشد؛ NTFS و فایل‌سیستم‌های معمول لینوکس پشتیبانی می‌کنند، برخی mountهای خاص ممکن است نکنند.
- پس از انتشار فایل، یک تراکنش SQL تصویر و فیلدهای سازگاری Job را ثبت می‌کند. اگر تراکنش خطا دهد، همان فایل جدید حذف می‌شود؛ خروجی‌های قبلی batch باقی می‌مانند.
- سقوط سخت بین فایل و commit می‌تواند orphan باقی بگذارد. فایل‌سیستم و SQL یک تراکنش واحد ندارند؛ ادعای exactly-once کامل نداریم. ابزار `scripts/audit_gallery.py` فقط گزارش می‌دهد و هیچ فایل/رکوردی را حذف نمی‌کند.

بودجهٔ ۳۲ MiB JSON یعنی یک پاسخ قدیمی base64 لزوماً نمی‌تواند فایل ۶۴ MiB حمل کند؛ سقف فایل و سقف envelope دو قید جدا هستند. URL راه ترجیحی خروجی بزرگ است. عبور پاسخ پس از ارسال از بودجه، `unknown` است و خودکار تکرار نمی‌شود.

## نمایش و تحویل

- اصل تصویر هرگز re-encode نمی‌شود. پیش‌نمایش مشتق WebP حداکثر ۶۴۰×۶۴۰ و کیفیت ۷۸ است؛ کیفیت آن مربوط به پیش‌نمایش است، نه کیفیت فایل دانلود.
- ساخت پیش‌نمایش به دو کار هم‌زمان محدود است؛ فایل‌های بالای ۲۴ مگاپیکسل پیش‌نمایش ندارند و اصل قابل دریافت است. این قید از بازشدن چند تصویر خیلی بزرگ در حافظه جلوگیری می‌کند.
- اصل و پیش‌نمایش احراز هویت دارند. پاسخ خصوصی و no-store است. اصل با FileResponse تحویل می‌شود و HTTP Range در نسخهٔ وابستگی تست‌شده کار می‌کند. برنامه فایل کامل را برای هر دانلود وارد RAM نمی‌کند.
- گالری هر بار ۲۴ خروجی می‌خواند؛ سقف هر صفحه ۱۰۰ است. cursor بر اساس job_id و position است و ترتیب پایدارِ شناسه دارد؛ ترتیب زمانی نیست. برای دیدن خروجی‌های جدید Refresh بزنید.
- ZIP هر Job فایل‌های اصل را با ZIP_STORED روی دیسک جمع می‌کند؛ دوباره فشرده‌سازی نمی‌کنیم. سقف ۱۰ فایل و مجموع ۶۴۰ MiB؛ فقط دو export هم‌زمان. سفارش running قابل export نیست.
- پس از پایان ارسال ZIP، cleanup فایل موقت و آزادسازی جایگاه انجام می‌شود. در خطای ساخت نیز cleanup انجام می‌شود. Kill سخت ممکن است فایل export موقت باقی بگذارد؛ audit گزارش می‌کند.
- پیش‌نمایش‌های cache ممکن است پس از حذف Job باقی بمانند؛ به‌علت بررسی مجدد ردیف و اصل، از مسیر API در دسترس نیستند. پاک‌سازی خودکار retention هنوز اضافه نشده است.

## اندازه‌گیری محلی

فایل `TRANSFER_BENCHMARK.json` نتیجهٔ یک اجرای مصنوعی روی PNG حدود ۷٫۳۳ MiB است: peak تخصیص Python در مرحلهٔ ذخیره، از ۱۷٫۰۹۹ MiB در روش قبلی به ۰٫۸۹۹ MiB در روش قطعه‌ای رسید. ورودی base64 قبل از شروع اندازه‌گیری ساخته شده بود. این عدد RSS کل، حافظهٔ Chrome، parse پاسخ JSON یا throughput تولید تصویر نیست. زمان همان اجرای واحد ۰٫۰۴۳۲ در برابر ۰٫۰۲۸۶ ثانیه بود؛ از یک اجرا SLA یا افزایش سرعت عمومی نتیجه نمی‌گیریم.
