# معماری مهندسی هم‌زمانی و تولید چند تصویر — Ninja Image Hub v0.3

> **سند تاریخی:** این فایل وضعیت **v0.3** را توصیف می‌کند و تاریخ آن ۳ نوامبر ۲۰۲۶ است. برای رفتار فعلی v0.6 به `OPERATIONS_V6_FA.md`، `ARCHITECTURE_V5_FA.md` و `FILE_PIPELINE_V5_FA.md` مراجعه کنید. محدوده‌های تنظیمات در جدول زیر با کد فعلی هم‌تراز شده‌اند، اما جزئیات پیاده‌سازی v0.3 ممکن است با v0.6 یکی نباشد.

## ۰. هدف، حدود و واقعیت سرویس

هدف کاربر: مدیریت چند حساب، ثبت آسان درخواست از پنل یا ایجنت DeepSeek، تولید چند خروجی در هر درخواست و مدیریت عملیاتی **۵۰۰ تصویر در پنجره ۵ ساعته**. هدف مطلوب = **۱۰۰ خروجی موفق در ساعت یا ۱٫۶۶۷ خروجی موفق در دقیقه**. این صرفاً هدف محصول است؛ هیچ حساب Plus ظرفیت مشخص یا تضمین‌شده‌ای برای تحقق آن ندارد.

- این پروژه برای یادگیری و تست محلی است. استخراج خودکار خروجی ChatGPT.com با مرورگر خلاف شرایط فعلی استفاده OpenAI است و احتمال محدودیت/تعلیق دارد. استقرار تجاری باید از API رسمی یا ارائه‌دهنده مجاز استفاده کند.
- افزایش تعداد اکانت یا تب‌ها **راه مجاز دورزدن سهمیه نیست**. هرگاه ارائه‌دهنده محدودیت اعلام کند، Job مرتبط `rate_limited` می‌شود و **همان حساب** به حالت cooldown می‌رود. هیچ چرخش خودکار حساب، تغییر هویت، حل CAPTCHA یا مخفی‌کاری ضدتشخیص در این پیاده‌سازی وجود ندارد.
- تعداد درخواست‌ها در صف و تعداد Job در حال اجرا، به معنی تعداد تصویر تولیدشده نیست؛ ملاک خروجی‌های ذخیره‌شده و معتبر است.

## ۱. پاسخ فنی: یک حساب چند تصویر؟

بله؛ اما سه مفهوم مستقل وجود دارد:

1. **Images per job (`n`)**: از یک پرامپت N خروجی می‌خواهیم. در Gateway فعلی `n=1..10` مستند شده است؛ هرچند خروجی‌ها ممکن است نوبتی تولید شوند، ناقص باشند یا رد شوند. در Hub، سقف پیش‌فرض محافظه‌کارانه `MAX_BATCH_IMAGES=4` است و تا ۱۰ قابل تنظیم است.
2. **Parallel jobs per account**: چند Job جدا در چند تب مرورگر برای **یک حساب** اجرا می‌شوند. `gpt-web-gateway` مقدار `MAX_CONCURRENT_JOBS=1..5` (پیش‌فرض خود پروژه ۳) را مستند کرده است. Hub از تنظیم قابل ویرایش `parallel_limit` برای هر حساب و سقف `GATEWAY_MAX_TABS` استفاده می‌کند.
3. **Parallel accounts / processes**: هر حساب مرورگر، نشست، فرایند و کلید محلی اختصاصی دارد. تعداد فرایندهای مجاز با `MAX_RUNNING_ACCOUNTS` محدود می‌شود؛ ظرفیت حافظه و CPU اهمیت دارد.

**مثال:** دو حساب، هر حساب ۲ Job هم‌زمان، هر Job درخواست ۳ تصویر: حداکثر ۴ *درخواست* هم‌زمان داریم، نه ۱۲ تصویر هم‌زمان تضمین‌شده. `n=3` لزوماً به معنی تولید سه تصویر در یک لحظه نیست و ممکن است زمان هر Job چند برابر شود.

**منبع:** https://github.com/stufently/gpt-web-gateway ؛ اسناد API رسمی با پارامتر `n` برای Image API با URL https://developers.openai.com/api/docs/guides/image-generation . این دو مسیر را یکسان فرض نکنید.

## ۲. معماری v0.3

```text
            Web Dashboard                    DeepSeek / Agent Client
           (cookie + CSRF)                      (Bearer API key)
                    |                                  |
                    +------------------+---------------+
                                       |
                           FastAPI, 1 process only
                                       |
                                PostgreSQL/SQLite
                                   jobs table
                         | queued | running | result |
                                       |
                         Fair Dispatcher (round-robin)
                    per-account cap / global cap / cooldown
                      /       |               \\
                 Account A Account B        Account C
                 Gateway   Gateway          Gateway
                  1..5 tabs / instance + isolated profile
                      \\       |               /
                         Outputs: job_images table
                          (N output rows per job)
                                Gallery + Agent API
```

- **صف پایدار**: وضعیت `queued` در پایگاه داده می‌ماند؛ این صف، حافظه ThreadPool نیست.
- **در حال اجرا**: scheduler قبل از ارسال به ThreadPool وضعیت را `running` می‌کند؛ تعداد Thread محدود است؛ از Thread برای هزاران درخواست queued استفاده نمی‌شود.
- **انصاف**: هر دور یک جایگاه به هر حساب واجد شرایط اختصاص می‌یابد؛ سپس دورهای بعدی، با توجه به محدودیت‌ها. حساب دارای صف بلند نباید حساب دیگر را گرسنه کند. معیار انصاف Job است، نه تعداد تصویر؛ در آینده weighted-fair برحسب هزینه واقعی لازم می‌شود.
- **پروسه‌ واحد**: Supervisor و Dispatcher در همان فرایند FastAPI هستند. اجرای هم‌زمان چند Uvicorn Worker / چند Replica باعث ناهماهنگی می‌شود؛ برای HA باید lease اتمیک PostgreSQL و worker خارج از فرایند پیاده کرد.
- **دو سطح Backpressure**: اول `MAX_PENDING_JOBS` در Hub و سپس صف کوچک Gateway؛ به Gateway درخواست بی‌حساب ارسال نمی‌شود.
- **سقف‌های مستقل**: `GLOBAL_MAX_INFLIGHT`، `min(account.parallel_limit,GATEWAY_MAX_TABS)`، `MAX_RUNNING_ACCOUNTS` و سقف n. لازم است همگی با هم بررسی شوند.

## ۳. تنظیمات پیشنهادی اولیه (برای **تست کم‌حجم، نه تضمین عملکرد Plus**)

| کلید | پیش‌فرض | محدوده معتبر | توضیح |
|---|---:|---:|---|
| `MAX_RUNNING_ACCOUNTS` | 2 | 1..16 | سقف فرایندهای Chrome؛ اول RAM را اندازه بگیر |
| `GLOBAL_MAX_INFLIGHT` | 4 | 1..16 | سقف درخواست هم‌زمان کل Hub؛ *نه* سهمیه ارائه‌دهنده |
| `GATEWAY_MAX_TABS` | 3 | 1..5 | سقف تب هم‌زمان Gateway؛ به هنگام Start worker اعمال می‌شود |
| `parallel_limit` (در هر اکانت) | 2 | 1..5 | در پنل قابل ویرایش؛ حد مؤثر `min(..., GATEWAY_MAX_TABS)` |
| `MAX_PENDING_JOBS` | 1000 | 1..10000 | درخواست‌های منتظر در DB؛ بلافاصله به Thread تبدیل نمی‌شوند |
| `MAX_BATCH_IMAGES` | 4 | 1..10 | تعداد تصویر در هر Job در Hub و Gateway |
| `PROVIDER_COOLDOWN_MINUTES` | 30 | 1..240 | توقف ارسال درخواست جدید برای همان اکانت پس از 429 |
| `MIN_TURN_STAGGER_SEC` (Gateway) | 10 | ثابت در این نسخه | فاصله شروع نوبت‌ها در تب‌های مختلف |
| `MIN_JOB_GAP_SEC` (Gateway) | 60 | ثابت در این نسخه | فاصله نوبت‌ها در هر تب؛ در batch نیز اعمال می‌شود |

افزایش مقدارها باید بر اساس نتایج آزمایش محدود و مطابق شرایط ارائه‌دهنده باشد، نه برای عبور از محدودیت حساب. مقدار `parallel_limit` اگر از `GATEWAY_MAX_TABS` بزرگ‌تر باشد، در عمل به سقف Gateway محدود خواهد شد. تغییر `GATEWAY_MAX_TABS` نیازمند Restart کردن Worker در حال اجراست؛ تغییر `parallel_limit` فقط برای Jobهای جدید و قابل زمان‌بندی اثر دارد.

## ۴. چرا سرعتِ واقعی را نباید از n یا تعداد تب حدس زد؟

کمیت‌های قابل اندازه‌گیری:

- `L` = متوسط *زمان واقعی* هر Job (ثانیه، شامل فواصل Gateway، رندر و انتظار)
- `Y` = میانگین تصاویر معتبرِ تحویل‌شده از هر Job (می‌تواند کمتر از n باشد)
- `C` = تعداد Jobهای واقعاً فعال/پذیرفته‌شده در تمام حساب‌ها و ارائه‌دهنده
- `U` = ضریب بهره‌برداری قابل اتکا (پیشنهاد طراحی اولیه ۰٫۷؛ عددی فرضی)

تخمین تئوریک خروجی در ساعت: `R ≈ C × 3600 × Y × U / L`؛ این فرمول **فرض می‌کند درخواست‌ها واقعاً توسط ارائه‌دهنده پذیرفته شده‌اند** و اثر سهمیه‌های طولانی‌مدت یا تأخیرهای غیرخطی را نمی‌سنجد. تصویرهای ردشده، لاگین منقضی، محدودیت سهمیه و توقف سرویس، ظرفیت واقعی را پایین می‌آورند.

مثال فرضی (نه نتیجه آزمایش): اگر هر Job فقط یک تصویر صحیح بدهد (`Y=1`)، زمان ۹۰ ثانیه (`L=90`)، ظرفیت مفید چهار Job (`C=4`) و بهره‌برداری ۷۰٪ (`U=.7`) باشد، حاصل تئوریک ۱۱۲ تصویر در ساعت است؛ اندکی بالاتر از ۱۰۰، و **حاشیه اطمینان کمی** دارد. اگر زمان به ۱۵۰ ثانیه برسد، نرخ تئوریک فقط ۶۷٫۲ در ساعت خواهد بود. برای هدف واقعی باید تست با شرایط مجاز ارائه‌دهنده و ظرفیت اعلام‌شده API انجام شود.

## ۵. مدیریت خطا: وضعیت‌ها و تصمیم به Retry

| وضعیت | معنی | Retry خودکار؟ |
|---|---|---|
| `queued` | در DB ثبت شده و هنوز ارسال نشده؛ حساب ممکن است خاموش باشد | به‌محض آماده‌شدن Worker، dispatch می‌شود |
| `running` | Hub فراخوانی را شروع کرده است | خیر |
| `completed` | تمام N فایل در Gallery ثبت و قابل دریافت‌اند | نیاز نیست |
| `partial` | حداقل یک تصویر ذخیره شده، اما N فایل کامل نیست | خیر؛ بررسی انسانی |
| `failed` | خطای قطعی/اعتبارسنجی/پاسخ منفی | خیر؛ بررسی دلیل |
| `rate_limited` | محدودیت صریح ارائه‌دهنده؛ حساب cooldown دارد | خیر؛ بدون چرخش حساب |
| `unknown` | پاسخ از دست رفته یا فرایند وسط کار ری‌استارت شده؛ ممکن است تصویر upstream تولید شده باشد | **هرگز**، چون می‌تواند تولید دوباره باشد |
| `canceled` | قبل از dispatch از صف خارج شد | خیر |

قواعد حیاتی: **هیچ retry خودکار پس از timeout یا قطع اتصال بعد از ارسال**؛ فقط Retry دستی بعد از بررسی. `idempotency_key` در DB تضمین می‌کند ارسال تکراری همان درخواست با همان کلید، Job جدید نسازد. این کلید مانع تولید تکراری در Gateway بیرونی پس از قطع پاسخ نمی‌شود. پایان برنامه با SIGTERM در حالت Graceful منتظر Job جاری می‌ماند؛ در Kill سخت، Jobهای `running` در بالا آمدن بعدی `unknown` می‌شوند و **queued** سالم می‌مانند.

## ۶. ذخیره خروجی و کیفیت

- `n` خروجی = `job_images` با `position=0..n-1`؛ هر خروجی `image_width/height/format/bytes/sha256` مستقل دارد.
- فایل خام دریافتی از Gateway *بدون Re-encode* ذخیره می‌شود. تشخیص فرمت واقعی با Pillow و بررسی ابعاد و حداکثر ۶۴ MiB برای هر خروجی انجام می‌شود.
- `Best/Balanced/Draft` در browser mode فقط **راهنمای پرامپت** است، نه `quality=high/medium/low` رسمی API. **نمی‌توان کیفیت رندر را با این انتخاب تضمین کرد.**
- اگر Gateway خروجی بی‌کیفیت یا فشرده برگرداند، Hub نمی‌تواند کیفیت از دست‌رفته را بازیابی کند. ذخیره فایل اصلی به معنی تولید حداکثر رزولوشن نیست.
- URLهای تصویر Gateway محدود به `127.0.0.1` و پورت همان Worker هستند؛ URL خارجی، Redirect و مسیر نامعتبر رد می‌شوند.
- دانلود اول از مسیر قدیمی `/api/images/{job_id}` همچنان ممکن است؛ برای همه خروجی‌ها `/api/images/{job_id}/{position}` و در Agent مسیر متناظر `/v1/images/{job_id}/{position}` وجود دارد.

## ۷. تست بار و معیار قبولی

این آزمایش‌ها باید **فقط روی شبیه‌ساز یا ارائه‌دهنده‌ای با دسترسی و مجوز روشن** اجرا شوند، نه برای عبور از سهمیه ChatGPT Plus.

1. **Unit**: n نامعتبر (۰، بزرگ‌تر از سقف)، idempotency تکراری و متناقض، تابع validation و هش، SSRF، migration.
2. **Concurrency**: دو حساب، یکی ۶ Job و دیگری ۱ Job، با سقف global و per-account؛ بررسی اینکه حساب کم‌کار گرسنه نمی‌شود. تست محدودکننده با Event در Worker جعلی.
3. **Durability**: بستن ناگهانی پردازش؛ queued باقی بماند، running unknown شود؛ عدم ارسال دوباره خودکار.
4. **Fault injection**: 429 cooldown فقط همان حساب؛ 502/قطع پاسخ وضعیت unknown و بدون retry؛ n جزئی خروجی partial و عدم حذف فایل‌های سالم.
5. **Memory**: مصرف RAM برای ۱، ۲، ۳ و ۵ تب (هر حساب) و مصرف Disk برای batchهای بزرگ؛ از اندازه‌گیری `RSS` فرایندهای Chrome و P95 پاسخ استفاده شود.
6. **Performance/SLO**: تعداد خروجی موفق در ۵ ساعت، P50/P95 زمان هر Job، صف بیشینه، نرخ partial/unknown/429، RAM P95 و هزینه به ازای خروجی. برای هدف ۵۰۰، پذیرش صرفاً زمانی است که **≥۵۰۰ فایل معتبر در بازه ۵ ساعته** تحویل شود، بدون عبور از محدودیت سرویس.

در پنل `/api/queue` تعداد queued/running، ظرفیت global، cooldown حساب‌ها و `observed_images_last_hour` و P50/P95 مشاهده‌شده از Jobهای قبلی نمایش داده/در دسترس است. داده آزمایش شبیه‌سازی‌شده پیش‌بینی سرعت حساب Plus نیست. اگر نمونه کمتر از حد مناسب باشد، به آن اعتماد نکنید.

## ۸. خطرات و بدهی‌های فنی باقیمانده

- **عدم HA:** هنوز نیازمند queue/lease مستقل برای چند Replica هستیم؛ الان `--workers 1` اجباری است.
- **تغییر سورس Gateway:** selectorها، format پاسخ و login UI ممکن است تغییر کنند. نصب Gateway باید pin و برای نسخه جدید test شود.
- **سرعت/سهمیه نامعلوم:** حتی `GATEWAY_MAX_TABS=5` تضمین پذیرش از upstream نیست. برای کار روزانه ۱۵ هزار عکس از API رسمی یا ارائه‌دهنده مجاز استفاده شود.
- **پشتیبانی از شناسه حساب:** plan label دستی است؛ تشخیص خودکار Plus قابل اتکا نیست.
- **حذف و آرشیو:** تا وقتی queued/running باقی است، Archive مسدود می‌شود؛ queued را از Jobs با Cancel خارج کنید. Stop با running ممنوع است.
- **کلید idempotency:** کلید را خود Client باید برای Retry شبکه تکرار کند؛ تغییر کلید در Retry می‌تواند سفارش تازه بسازد.
- **عدم تضمین نتیجه اتمیک بین دیسک و DB:** فایل خام قبل از row ثبت می‌شود؛ قطع برق در این فاصله ممکن است فایل orphan ایجاد کند. به scrub/reconcile آفلاین برای نسخه Production نیاز داریم.
- **امنیت:** کوکی‌های browser به اندازه رمز حساب حساس هستند. Portهای Gateway روی loopback، پنل پشت SSH tunnel؛ HTTPS و احراز هویت الزامی برای انتشار عمومی. چند حساب حق دسترسیِ جداگانه برای مشتریان مختلف به معنی جداسازی tenancy چندکاربری نیست؛ این MVP فقط پنل یک ادمین دارد.

## ۹. دستور کار ایجنت توسعه (غیرقابل حذف از acceptance criteria)

- هر توسعه باید تست هم‌زمانی، تعداد تصویر خروجی، اعتبارسنجی مسیر دانلود و حفظ داده‌های قبلی را اجرا کند.
- هیچ مخفی‌کاری، حل challenge، چرخش خودکار حساب برای عبور از محدودیت یا ادعای تضمین ۵۰۰ تصویر در ۵ ساعت بدون اندازه‌گیری مجاز اضافه نکن.
- ممنوع: شروع دوباره Job `running/unknown` بدون تأیید انسانی، پاک‌کردن تصاویر `partial`، نادیده‌گرفتن `rate_limited`، افزایش بی‌نهایت Thread/Queue.
- آزمون قبولی: `python -m pytest -q` و `node --check frontend/app.js`، سپس mock integration و بازبینی واقعی پنل. تست Plus واقعی خارج از دامنه تست خودکار است.
